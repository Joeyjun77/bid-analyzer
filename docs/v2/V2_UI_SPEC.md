# V2_UI_SPEC — 화면 재구축 명세

> 대상: Claude Code 세션
> 목적: 마스터플랜 U 트랙(U0~U3)의 화면·컴포넌트 명세
> 확정 전제: 사용 환경 = **PC 사무실** / Mode A 곡선 = **불필요, 추천값 하나로 충분**
> 메모리 준수: `feedback_app_role_info_provider` — 정보 제공 도구, "확정/제출" 금지

---

## 0. UI 재구축의 이유

진단(DIAGNOSIS §3)이 드러낸 사실: 한전·LH·교육청·조달청(입찰의 ~80%)은
WIN-zone이 0%다. 낙찰이 구조적으로 운에 가깝다.

현재 UI는 모든 발주처에 "추천사정률 하나"를 동일하게 표시한다.
→ 한전 입찰에서도 사용자가 "낙찰 가능"이라 오인.
→ 백엔드를 2-모드로 정직하게 바꾸면서 UI를 안 바꾸면, 정직한 엔진 위에
   거짓 약속하는 화면이 얹힌다.

**UI 재구축은 B 트랙의 곁가지가 아니라 동급 트랙이다.**

## 1. 불변 원칙 4개

| # | 원칙 | 강제 수단 |

## 2. 화면 구조 — 단일 패널 + 모드 스위치

"Mode A도 추천값 하나면 충분" 확정 → ModeA/ModeB 패널 분리 불필요.
**패널 하나, 모드는 prop으로 분기.**

```
┌──────────────────────────────────────────┐
│  한국전력공사 경기본부 · 전기              │  ← 헤더 (발주사·종목)
│  [ 안착 모드 ]                             │  ← ModeBadge
├──────────────────────────────────────────┤
│  추천 사정률      -0.21% (99.79%)          │  ← 양 모드 공통
│  추천 투찰금액    ₩ 418,773,294            │  ← fmtAdj() 듀얼표기
│                                            │
│  ── 모드별 이 줄만 스위치 ──               │
│  [안착] 하한 통과 확률  ████████░░ 87%     │  ← Mode B 메인 숫자
│  [공략] 예상 낙찰 확률  ███░░░░░░░ 24%     │  ← Mode A 메인 숫자
│                                            │
│  [안착] ⚠ 이 발주처는 낙찰이 운에 가깝습니다.│  ← 모드별 안내
│         목표는 하한 미달 탈락 방지.        │
│  [공략] ✓ 군시설은 낙찰 가능 구간 존재.    │
├──────────────────────────────────────────┤
│  ▸ 왜 이 추천인가 (PC라 우측 상시 노출)    │  ← WhyPanel
│    유사사례 n=39 · gap median 0.001        │
│    모드 판정: 안착 (gap p90 0.006 < 0.10)  │
└──────────────────────────────────────────┘
```

PC 환경 → 가로 공간 활용. WhyPanel은 모바일처럼 접지 않고 우측 사이드 상시 노출.

## 3. 모드별 화면 차이

| 요소 | 안착 모드 (Mode B) | 공략 모드 (Mode A) |
|------|--------------------|--------------------|
| 배지 | "안착 모드" | "공략 모드" |
| 메인 숫자 | 하한 통과 확률 (예: 87%) | 예상 낙찰 확률 (예: 24%) |
| "낙찰 확률" 표시 | **금지** | 허용 |
| 안내 문구 | "낙찰은 운에 가까움, 목표는 탈락 방지" | "낙찰 가능 구간 존재" |
| 추천값 개수 | 1개 | 1개 (곡선 비노출) |

곡선·전략 3종 카드 = 화면에 없음. 백엔드(B3)는 곡선 계산하되 최적점 1개만 UI 전달.

## 4. 컴포넌트 구조 — App.jsx 분할

현재 App.jsx 1,294줄 단일 파일 → 모드 기준 분할.

```
App.jsx                  (라우팅·상태, ~200줄)
├─ UploadView.jsx        (업로드 — 보존, 변경 최소)
├─ AnalysisView.jsx      (모드 판정 → RecommendPanel에 prop 주입)
│   ├─ ModeBadge.jsx     (안착/공략 배지 — 신규 핵심)
│   ├─ RecommendPanel.jsx (★ 단일 패널 — mode prop으로 분기)
│   └─ WhyPanel.jsx      (왜 이 추천인가 — PC 사이드 상시노출)
├─ HistoryView.jsx       (실적 — bid_rate 공간 KPI로 교체)
└─ lib/
    ├─ modeResolver.js   (agency_mode_lookup RPC 호출)
    └─ fmtAdj.js         (듀얼표기 — 보존)
```

`AnalysisView`가 `modeResolver`로 A/B 판정 → `RecommendPanel`에 `mode` prop 전달.
패널 자체는 하나, 내부에서 mode에 따라 메인 숫자·문구·배지 스위치.

## 5. 기존 UI 자산 처리

| 컴포넌트 | 처리 | 사유 |
|----------|------|------|
| 추천사정률 + 투찰금액 | 양 모드 유지 | 핵심 출력 |
| 조정범위 3단계(적극/기본/안전) | **폐기** | 점추정에 폭 입힌 구식 패러다임, 2-모드와 충돌 |
| 경쟁참고 접기 | 폐기 | WhyPanel로 흡수 |
| 금액대별 낙찰률 안내 | 영역별 하한통과율 안내로 교체 | bid_rate 공간 전환 |
| 이상치 경고 | 유지 | 유효 |
| `WinStrategyDashboard.jsx` | 분할 시 폐기 | 99.8525 하드코딩 버그 자연 소멸 |
| `fmtAdj()` | 보존 | 좋은 자산 |
| 낙찰 컬럼 ✓/✗ | 유지 (HistoryView) | 실적 추적 |

## 6. U 트랙 단계 (마스터플랜 §5 재확인)

| 단계 | 시기 | 작업 | 백엔드 의존 |
|------|------|------|-------------|
| U0 | Week 1~2 | App.jsx 분할 + RecommendPanel 골격(mock 데이터) | 없음 — 선행 |
| U1 | Week 2 | ModeBadge + modeResolver.js — agency_mode_lookup 연결 | B1 |
| U2 | Week 3~5 | RecommendPanel 안착 모드 실데이터 — 하한 통과 확률 | B2 |
| U3 | Week 6~7 | 같은 패널 공략 모드 prop 추가 | B3 |

U0를 mock으로 선행 → B2 엔진 나오면 즉시 연결. 빈 패널에 mock 넣어 화면 흐름 먼저 확정.
U3는 작업량 최소 — 같은 패널에 prop만 추가 (곡선 없으므로).

## 7. /evaluate 모드 표시 게이트

마스터플랜 §6의 4번째 게이트.

> **모드 표시 게이트**: 안착 모드 입찰 화면에 "낙찰 확률" 문자열이
> 렌더링되면 FAIL.

진단 교훈("낙찰은 80% 영역에서 운")을 화면 레벨에서 강제.
RecommendPanel이 `mode==='B'`일 때 "낙찰 확률" 텍스트를 출력하지 않는지
빌드/테스트 단계에서 검증.

## 8. 배포 워크플로 (기존 패턴 유지)

```
src/ 파일 교체
  → npx vite build (검증)
  → git add/commit/pull --rebase/push
  → Vercel 1~2분 대기
  → hard refresh 확인
```

컴포넌트 분할은 한 번에 하지 말고 단계적으로 — U0에서 RecommendPanel 먼저
분리, 빌드 통과 확인 후 다음 컴포넌트. 각 분할마다 `npx vite build` 통과 필수.
