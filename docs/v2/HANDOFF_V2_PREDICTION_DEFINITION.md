# HANDOFF: 입찰분석기 V2 — 예측 시스템 정의

> 대상: Claude Code 세션
> 목적: V5~V7 폐기 후 V2 예측 엔진 재설계의 **예측 대상 정의** 확정
> 상태: 설계 확정 단계 (코드 작성 전)
> 전제: `bid_records` 53,199건, 파일 업로드 파이프라인, G2B 수집, canonical_ag 정규화는 보존

---

## 0. TL;DR

V5~V7은 "사정률을 정확히 맞추는 것(MAE 최소화)"을 예측 목표로 삼아 정체했다.
V2의 예측 대상은 단 하나의 문장으로 재정의한다.

> **"우리가 사정률 X로 투찰했을 때, 이 입찰건에서 낙찰될 확률은 몇 %인가."**

사정률 예측은 목표가 아니라 이 확률을 계산하기 위한 **부품**이다.
시스템의 최종 출력은 숫자 하나가 아니라 곡선 `X → P(낙찰|X)`이다.

---

## 1. 예측의 정식 정의

### 1.1 최종 예측 대상

```
입력:  발주사 + 공사 메타데이터 + 기초금액 + 자사 적격심사 점수
출력:  함수 f(X) = P(낙찰 | 사정률 X)
       X = 자사가 선택하는 사정률 후보
```

### 1.2 "낙찰"의 구조 분해

낙찰되려면 **두 개의 독립 조건**을 동시에 통과해야 한다.

**조건 A — 가격 조건 (WIN zone 진입)**

```
낙찰하한가  ≤  자사 투찰금액  ≤  (1위 경쟁자 투찰금액 직전)
```

- 하한 미달 → 입찰가격 점수 미달 → 자동 탈락
- 상한 초과(= 더 낮게 쓴 적격 업체 존재) → 그 업체가 낙찰
- 전기 8천만~3억 구간 낙찰하한율 = 86.745% (교육자료 기준)

**조건 B — 적격심사 통과**

- 종합평점 95점 이상
- 시공경험(15) + 경영상태(15) + 입찰가격(70→65) = 95
- 자사 점수는 사전 계산 가능 → 거의 결정론적 (보통 P=1.0)

### 1.3 낙찰 확률 공식

```
P(낙찰 | X) =
    P( 자사투찰 ≥ 낙찰하한가 )      ← 예정가격 분포에서 계산
  × P( 자사투찰 < 1위 경쟁투찰 )     ← 경쟁 분포에서 계산
  × P( 적격심사 통과 )              ← 보통 1.0 (사전 확인됨)

자사 투찰금액 = 기초금액 × (100% + X) × 낙찰하한율
```

앞 두 항은 모두 예정가격 분포 `P(예가)`에 의존한다(하한가도 경쟁가도 예가에서 파생).
실제 계산은 **사정률 분포 ⊛ 경쟁 분포의 컨볼루션**이다.

---

## 2. 두 개의 미지수 — 분포로 추정

### 2.1 미지수 1: 예정가격 (사정률)

복수예비가격 메커니즘은 본질적으로 난수다.

- 15개 예비가격 중 4개 추첨 → 산술평균 → 예정가격
- C(15,4) = 1,365 조합 → 구조적 노이즈 플로어 ~0.642% MAE
- **예정가격은 점으로 예측 불가. 분포로만 예측 가능.**

```
예측 출력: 발주사별 사정률 분포
  P(사정률) ~ 발주사 고유 분포 (기초/예가 ratio 분포)
  → P10 / P25 / P50 / P75 / P90
```

학습 가능한 신호: 발주사별 복수예비가격 작성 편향(±3%, ±2%, +0~-6% 등 사정범위 차이).
노이즈 플로어는 못 줄이지만 **분포의 위치·폭은 발주사별로 다르고 학습 가능**하다.

### 2.2 미지수 2: 경쟁자 1위 투찰금액

V5~V7이 거의 다루지 않은 영역. WIN zone 상한은 경쟁자가 결정한다.

```
예측 출력: 경쟁 강도 분포
  P(1위 경쟁자 사정률) ~ 발주사 × 금액대 × 종목별 경쟁 분포
  → 과거 동일 조건 입찰에서 "1위와 하한율 사이 간격"의 분포
```

경쟁자도 같은 낙찰하한율을 알고 비슷한 구간에 몰린다.
1위는 거의 항상 하한율 바로 위에 형성됨 → "얼마나 바로 위인가"의 분포가 핵심.

## 3. 출력 형태: 단일값이 아니라 곡선

시스템의 진짜 출력은 함수 `X → P(낙찰|X)`.

전형적 곡선 모양:

- X 너무 낮음(공격적) → 하한 미달 위험 → P 낮음
- X 적정 → 하한 통과 + 경쟁 우위 → P 최대 (peak 존재)
- X 너무 높음(안전) → 경쟁자에게 밀림 → P 낮음

곡선에서 3개 지점을 뽑아 전략으로 제시:

| 전략   | 선택 기준                          | 특성                          |
|--------|------------------------------------|-------------------------------|
| 공격형 | P(낙찰) 곡선의 좌측 어깨            | 낙찰 시 마진↓, 하한 미달 감수  |
| 균형형 | P(낙찰) 최대점                     | 낙찰 확률 자체를 최대화        |
| 안정형 | 하한 미달 확률 ≤5% 제약 하 최대 P   | 탈락 리스크 최소, 마진 보존    |

각 전략 카드에 **명시적 낙찰 확률 %**를 표시한다.
올바른 출력 예: `"사정률 -0.134% → 낙찰확률 38%, 균형형"`
잘못된 출력 예: `"추천사정률 -0.134%"` (점추정 사고방식)

## 4. V5~V7 대비 결정적 차이

| 항목         | V5~V7                  | V2 (재정의)                       |
|--------------|------------------------|-----------------------------------|
| 예측 대상    | 사정률 점추정          | 낙찰 확률 곡선                    |
| 평가 지표    | MAE 0.542%             | 낙찰 확률 calibration             |
| 경쟁자 모델  | 거의 없음 (참고용 접기)| 1급 미지수로 분포 추정            |
| 출력         | 추천값 1개 + 조정범위  | 전략 3종 + 각 낙찰확률            |
| "정확함"의 뜻| 사정률 오차 작음       | 예측 낙찰확률 = 실제 낙찰률       |

**V5~V7이 MAE를 줄여도 낙찰률 5.0%에 머문 이유:**
사정률을 정확히 맞춰도 경쟁자보다 높게 쓰면 진다.
경쟁 분포를 모델링하지 않으면 낙찰 예측이 원리적으로 불가능하다.

## 5. 검증 정의 (이게 없으면 V2도 실패)

예측이 "맞았다"의 정의 = **calibration**.

> 시스템이 "낙찰확률 30%"라 말한 입찰건 100개를 모으면,
> 그 중 실제로 약 30건이 낙찰되어야 한다.

| 지표 등급 | 지표               | 비고                              |
|-----------|--------------------|-----------------------------------|
| 1차       | calibration error  | 예측 낙찰확률 vs 실제 낙찰률 괴리 |
| 2차       | WIN zone 진입률     | 조건 A만 따로 측정                |
| 보조      | 낙찰률 절대값       | n 작아 신호 약함, 비즈니스 최종목표|
| 폐기      | MAE                | 구조적 한계라 1차 지표 부적합     |

## 6. 예측 엔진 V2 파이프라인

```
입력: 발주사 + 공사 메타 + 기초금액
  ↓
[Agency Resolver]
  - canonical_ag 매칭 (Phase 14 자산 활용)
  - 계층적 fallback: 발주사ID → 발주사유형 → 지역 → 전역
  ↓
[Distribution Estimator] — 사정률 분포
  - n≥30:      경험분포 직접 사용
  - 10≤n<30:   Bayesian shrinkage (prior = 발주사 유형)
  - n<10:      prior 우세
  ↓
[Competition Estimator] — 경쟁 분포
  - 데이터 충분 시: 발주사×금액대×종목별 경험분포
  - 데이터 부족 시: "1위 = 하한율 + α" prior
  ↓
[Calibration Layer]
  - 발주사별 rolling bias 보정 (예: LH -0.465)
  - bias 보정 *전*/*후* 분포 모두 저장 (이중 보정 위험 차단)
  ↓
[Win Probability Engine]
  - 사정률 분포 ⊛ 경쟁 분포 컨볼루션
  - 출력: 곡선 f(X) = P(낙찰|X)
  ↓
[Strategy Generator]
  - 곡선에서 공격/균형/안정 3지점 추출
  - 각 지점에 명시적 낙찰확률 부착
```

## 7. 다음 작업: 데이터 충분성 진단 (BLOCKER)

V2 예측은 경쟁 분포 추정 가능 여부에 달려있다. **코드 작성 전 반드시 확인.**

진단 쿼리 목표:

1. `bid_details` 600건에 **경쟁사별 투찰가**가 있는가
2. `bid_records` 53,199건에 **1위/낙찰자 투찰금액 컬럼**이 있는가
3. 경쟁사별 사정률을 역산할 수 있는가 (낙찰자 투찰가 + 기초금액 + 낙찰하한율 → 사정률)

분기 결정:

- **경쟁 데이터 있음** → 경쟁 분포를 데이터 기반으로 추정
- **경쟁 데이터 없음** → "1위 = 하한율 + α" 단순 prior에서 시작, 이후 누적 데이터로 보정

### 진단 쿼리 (Supabase MCP, project `sadunejfkstxbxogzutl`)

```sql
-- 1. bid_records 스키마 확인 — 1위/낙찰자 투찰금액 컬럼 존재 여부
SELECT column_name, data_type
FROM information_schema.columns
WHERE table_name = 'bid_records'
ORDER BY ordinal_position;

-- 2. bid_details 스키마 확인 — 경쟁사별 투찰가 존재 여부
SELECT column_name, data_type
FROM information_schema.columns
WHERE table_name = 'bid_details'
ORDER BY ordinal_position;

-- 3. bid_details 실제 데이터 샘플 — 한 입찰건당 경쟁사 row 수 확인
SELECT bid_id, COUNT(*) AS competitor_rows
FROM bid_details
GROUP BY bid_id
ORDER BY competitor_rows DESC
LIMIT 20;

-- 4. 낙찰자 투찰금액 보유 건수 — 경쟁 모델링 가능 표본 크기
SELECT COUNT(*) AS total,
       COUNT(*) FILTER (WHERE 낙찰자_투찰금액_컬럼 IS NOT NULL) AS with_winner_bid
FROM bid_records;
-- ※ 4번 쿼리는 1번 결과로 실제 컬럼명 확인 후 수정해서 실행할 것
```

## 8. 작업 원칙 (절대 준수)

- **A안 원칙**: `predictions_v2`는 INSERT-only. 매칭된 과거 예측 UPDATE 금지.
- **데이터 안전**: `bid_records` DELETE 금지. `bid_predictions.opt_adj` UPDATE 명시적 확인 없이 금지. DROP TABLE 명시적 확인 없이 금지.
- **이중 보정 주의**: bias 보정 레이어가 기존 OPT_OFFSET / prediction_bias와 중복 적용되지 않도록 검증.
- **마이그레이션**: 기존 `bid_predictions` 855건은 V2로 이관하지 않음 (점추정→분포 역변환은 정보 손실). 53K `bid_records`는 학습용으로만 재사용.
- **dual-run**: V2 코드 작성 전 검증 인프라부터 설계. V6/V2 6~8주 병렬 운영 후 우세 확인 시 V6 retire.

## 9. 미해결 결정 사항 (Decision Memo에서 확정 필요)

코드 작성 전 아래 4건을 글로 확정한다.

1. **1차 KPI**: WIN zone 진입률(측정 쉬움/신호 약함) vs 낙찰률(측정 어려움/신호 강함) vs 기대수익(비즈니스 정렬/마진데이터 필요)
2. **학습 단위**: 발주사ID vs 발주사유형 vs 계층(Bayesian) — V7 핸드오프 미해결 4건 여기서 종결
3. **손실함수**: calibration loss vs WIN zone hit vs 비대칭(under-bid 페널티↑)
4. **경쟁 모델 시작점**: 데이터 기반 vs prior 기반 — 7절 진단 결과에 따라 결정
