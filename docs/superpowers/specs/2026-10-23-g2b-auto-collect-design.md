# G2B 양식 자동 수집 (1차: 나라장터·경기·전기공사업) — 설계

작성 2026-10-23 · 상태: 사용자 결정 반영(문서 승인 대기)

## 1. 왜

- 지금은 인포21에서 등록한 입찰 건마다 bidq G2B 엑셀을 하나씩 받아 업로드한다. 손이 많이 가서 업로드가 몰리거나 끊긴다(8월 이후 공백 → 10/20·10/23 몰아서 455건).
- 이 데이터는 G2B 양식 탭(발주처별 1위사정율·발주처사정율 빈도)과 투찰 카드의 '발주처 1위 이력'이 쓴다. 늦게 들어오면 투찰 판단에 쓸 이력이 비어 있다.
- 서버는 이미 나라장터 공공데이터로 개찰 결과·낙찰자·복수예비가·공고를 매일 수집한다. 빠진 재료는 A값뿐이었고, 기초금액 조회 API(`getBidPblancListInfoCnstwkBsisAmount`)로 받을 수 있음을 확인했다(2026-10-23, 2건 원 단위 일치).

**성공의 모습**: 나라장터 경기 전기공사업 공고는 엑셀을 올리지 않아도 개찰 다음 날 아침에 G2B 양식과 투찰 카드에 나타난다. 같은 공고를 엑셀로 올렸을 때와 값이 같다.

## 2. 목표 / 비목표 / 반목표

**목표**
- 나라장터(공고번호 `R…`) 개찰 공고 중 경기 지역 전기공사업 공고를 매일 자동으로 G2B 양식 형태(아래 §4 컬럼)로 만든다.
- 사용자가 직접 참여한 나라장터 공고는 지역과 무관하게 포함한다.
- 개찰 다음 날(D+1) 아침 8시(KST) 전에 화면에 반영한다.
- 2026-04(서버 수집 시작) 이후 과거분 중 엑셀이 없는 공고를 채운다.
- 초기에는 자동 수집 행에 표시를 붙여 엑셀 행과 구분하고, 집계에는 "자동 N건 포함"을 표기한다.
- 화면 노출은 엑셀 대조 합격 뒤에 켠다.
- 엑셀과 겹치는 공고로 자동 계산값이 맞는지 매일 대조한다.

**비목표 (1차에서 하지 않음)**
- 국방전자조달(D2B, 군부대)·한전 SRM·기타 공기업 자체 조달 공고. 7/1~10/23 엑셀 973건 중 43%(국방 28%·한전 11%·기타 4%)가 이쪽이며 나라장터 API로 받을 수 없다. 이 공고들은 엑셀 업로드를 계속 쓴다. 공개 API 존재 여부 조사는 별건.
- 예측 엔진(발주처 통계·예측값) 입력에 넣기 — 2단계(§9). 1단계에서 예측값은 하나도 바뀌지 않는다.
- 엑셀 업로드 기능 제거·변경.
- 전국·다른 업종.
- 2026-04 이전 과거분(그 기간은 엑셀 데이터가 분기 600~1,800건씩 이미 있고, 서버 API 행 자체가 없다).

**반목표 (기술적으로 돌아가도 실패로 보는 것)**
- 자동 계산값이 bid_records에 들어가 예측 엔진·자동 매칭·품질 집계가 조용히 바뀌는 것.
- 같은 공고가 엑셀 행과 자동 행으로 두 번 집계되는 것(빈도·이력이 부풀려짐).
- 검증 안 된 계산값을 엑셀 값처럼 구분 없이 보여 주는 것.
- 과거분 채우기나 대조 쿼리가 운영 DB IO를 소진하는 것(2026-10-21 사고 재발).

## 3. 제약

- Supabase SDK 금지, 기존 REST·RPC 패턴 유지. 서버 수집은 기존 edge function + pg_cron(`invoke_edge_function`) 방식.
- 공공데이터 키 한도: `prod_bid_public`(입찰공고정보서비스, 기초금액 API 포함) 하루 1,000회, `prod_scsbid_info`(낙찰정보서비스) 하루 1,000회. 현재 사용량은 공고 수집이 하루 약 50회, 개찰 결과 수집이 하루 20회.
- bid_records DELETE 금지. 매칭된 bid_predictions 보호값 UPDATE 금지(이번 설계는 둘 다 건드리지 않는다).
- 새 테이블은 만들 때 RLS ON + 권한 제한을 같은 마이그레이션에 넣는다(2026-10 스냅샷 노출 사고 교훈).
- 운영 DB에서 무거운 전수 쿼리 금지. 모든 쿼리에 statement_timeout, 과거분 처리는 밤에 소량씩 나눠서.
- 앱은 정보 제공 도구 — "확정/제출" 류 UI 없음.

## 4. 만들 값 (G2B 양식 컬럼)과 계산식

| 컬럼 | 출처 | 비고 |
|---|---|---|
| 개찰일·공고번호·공고명·발주처·1순위업체·사업자번호·참가자 수 | 개찰결과·낙찰자 API → bid_records API 행 | 이미 수집 중 |
| 1순위금액(bp) | 낙찰자 API → bid_records | 현재 API 행의 67%만 있음(유찰·미확정 제외) |
| 기초금액(ba)·예정가격(xp) | 복수예비가 API → `bid_prelim_sets.bssamt`·`plnprc` | 공고번호 본체(`bid_ntce_no`)로 연결. API 행의 89% |
| 낙찰하한율(fr) | 공고 원본 `bid_notices.raw_json->>'sucsfbidLwltRate'` | 원본은 30일 뒤 정리됨 → 없으면 공고 API 재조회 |
| A값(av) | 기초금액 API 항목 합 | `bidPrceCalclAYn='N'`이면 0 |
| 발주처사정율(ar1) | xp ÷ ba × 100 | 엑셀 대조 오차 ≤ 0.0001 |
| 1위사정율(br1) | (av + (bp − av) ÷ (fr/100)) ÷ ba × 100 | 엑셀 126건 중 125건 0.001 이내 일치 |
| 낙찰하한가(floor_price) | av + (xp − av) × fr/100 | 엑셀 126건 중 125건 10원 이내 일치 |

A값 = 국민연금(`npnInsrprm`) + 건강(`mrfnHealthInsrprm`) + 퇴직공제(`rtrfundNon`) + 노인장기요양(`odsnLngtrmrcprInsrprm`) + 산업안전보건관리비(`sftyMngcst`) + 안전관리비(`sftyChckMngcst`) + 품질관리비(`qltyMngcst`, `qltyMngcstAObjYn='Y'`일 때). 확인된 표본은 2건뿐이다. 환경보전비·하도급대금지급보증수수료·품질관리비의 포함 여부는 대조(§7)로 확정한다. 확정 전까지 원본 항목은 그대로 저장해 나중에 다시 계산할 수 있게 한다.

반올림·절사 규칙(엑셀은 사정률 소수 4자리)은 빌더가 엑셀 겹침 공고로 맞춘다.

## 5. 대상 고르기

1. 나라장터 공고만: 공고번호가 `R`로 시작.
2. 지역: `bid_notices.reg`에 '경기' 포함(참가 가능 지역). reg는 공고 테이블에 100% 남아 있다.
3. 업종 = 전기공사업: **가장 어려운 부분이다.** 9/1~7 경기 공고 271건 중 공고 업종(`cat`)이나 원본 주공종(`mainCnsttyNm`)으로 알 수 있는 것은 76건뿐이고, 195건(72%)은 둘 다 비어 있다.
   - 매일 수집(D+1)은 공고 원본이 아직 남아 있는 시점이라 원본 필드로 판별할 수 있을 것으로 본다.
   - 원본이 없는 과거분은 공고 API를 공고번호로 다시 조회해 판별한다.
   - 어느 필드(주공종명·면허제한 업종·공고 업종)가 엑셀의 '전기공사업'과 가장 잘 맞는지는 빌더가 엑셀 겹침 공고로 재현율을 측정해 정한다. 기준: 엑셀에 있는 나라장터 경기 전기 공고를 자동 판별이 95% 이상 잡을 것.
   - **보수적으로 판별한다(설계자 판단).** 공고 필드(공고 업종·주공종·면허 제한) 중 하나에 '전기공사업'이 있으면 포함한다(전기+통신·소방 복수 면허 포함). 필드가 모두 비어 공고명으로만 추정되는 공고는 넣지 않는다. 그 경우 공고 API를 다시 조회해 필드를 얻는다.
   - 정밀도는 엑셀로 잴 수 없다(엑셀에는 사용자가 고른 공고만 있음). 그래서 합격 판정 때 자동 판별로 들어간 공고 중 엑셀에 없는 것 30건을 공고명·면허로 수동 검수하고, 오분류 2건 이하를 기준으로 한다(설계자 판단).
4. 사용자가 참여한 공고(업로드된 예측이 있거나 `participated=true`)는 2·3 조건과 무관하게 포함.
5. 같은 공고의 엑셀 행이 있으면 화면에서는 엑셀 행이 우선이다. 자동 행은 만들되 대조용으로만 쓴다. 엑셀 행 판별은 공고번호 형식으로 한다(설계자 판단): 엑셀 행은 `R…-NNN`처럼 차수 접미사가 붙고, API 행은 `R…`로 붙지 않는다. 앱이 읽는 컬럼(`BID_RECORDS_COLS`)에는 `g2b`가 없으므로 이 컬럼에 기대지 않는다. 서버 쪽 판별은 `g2b` 값 유무를 써도 된다.

## 6. 저장과 흐름

**새 테이블 1개** (이름은 빌더 판단, 예: `g2b_auto_sheet`) — 공고번호 본체당 1행.
- 키: 공고번호 본체(`bid_ntce_no`), 차수.
- 값: §4 컬럼 전부 + A값 원본 항목(jsonb) + A값 적용 여부 + 출처 표시(어느 값이 어디서 왔는지) + 상태(완성 / 재료 부족: 어떤 재료가 없는지) + 계산 시각.
- 엑셀 겹침 대조 결과(엑셀 값과의 차이)를 같은 행이나 별도 뷰에 둔다.
- RLS ON, 로그인 사용자 SELECT만, 쓰기는 service_role만.
- **bid_records에는 쓰지 않는다.** 이게 1단계 격리의 핵심이다. 예측 엔진·자동 매칭·품질 집계는 bid_records를 읽으므로 새 테이블을 보지 않는다.

**매일 흐름 (KST)**
1. 01:10~01:40 복수예비가 수집(기존 cron 20~22).
2. 06:00 개찰결과·낙찰자 수집(기존 cron 2). 조회 창이 7일이라 하루 1,000건 한도에 늘 걸린다(7일 창 약 2,300건). 9월 엑셀 나라장터 공고 120건 중 104건(87%)만 API 행이 있다. **1단계에서는 이 cron을 바꾸지 않는다(설계자 판단).** cron이 bid_records에 넣는 API 행이 늘면 자동 매칭(match_pending_predictions)이 달라질 수 있어 "예측값 불변" 약속과 부딪힌다. 대신 새 함수가 대상 공고 중 API 행이 없는 것을 낙찰정보 API로 공고번호 조회해 **새 테이블에만** 저장한다(낙찰정보 키는 하루 20회만 쓰는 중). cron 창 조정은 2단계에서 다룬다.
3. 07:00 새 수집 함수: 최근 개찰 공고 중 대상(§5)이면서 아직 완성되지 않은 것을 골라 기초금액 API 호출(공고당 1회) → 계산 → 새 테이블에 저장. 재료가 없어 미완성인 행은 다음 날 다시 시도하고, 며칠(빌더 판단) 지나도 안 되면 포기 상태로 남긴다.
4. 하루 호출 예산: 새 함수에 300회 상한(키 한도 1,000 중). 대상은 하루 수십 건 수준.

**과거분 (2026-04 ~ 어제)**
- 같은 함수를 '과거분 모드'로 밤마다 상한 안에서 조금씩. 화면용은 엑셀 행이 없는 공고, 대조용(§7)은 엑셀 행이 있는 공고. 대조용을 먼저 처리한다.
- 원본이 정리된 공고는 업종·하한율 판별을 위해 공고 API를 추가로 조회한다(공고당 최대 2회 추가).
- 규모 추정: 경기 나라장터 공고 주 270건 × 약 29주 중 전기공사업만 → 기초금액 호출 수천 회 이하. 1~3주에 나눠 끝낸다. 진행 상태는 기존 `prepc_backfill_state`처럼 테이블에 남긴다.

## 7. 검증 (1단계의 핵심)

- 엑셀과 겹치는 공고(같은 공고번호 본체)마다 ba·av·xp·fr·bp·ar1·br1·floor_price를 엑셀 값과 비교한다.
- 합격 기준(2주 누적): ar1 오차 ≤ 0.0001이 99% 이상, br1 오차 ≤ 0.001이 98% 이상, floor_price 오차 ≤ 10원이 98% 이상, 업종 판별 재현율 95% 이상.
- 불일치 행은 원인(A값 항목, 하한율, 반올림 등)을 남겨 계산식을 고친다. A값 항목 구성은 여기서 확정한다.
- 결과는 SQL 한 번으로 볼 수 있게 한다(뷰 또는 함수). 운영 DB 부담이 없도록 새 테이블 범위에서만 계산한다.
- **대조 표본(설계자 판단)**: 기능이 켜진 뒤에는 나라장터 공고 엑셀이 줄어들 것이다. 그래서 합격 판정은 2026-04 이후 엑셀이 이미 있는 나라장터 경기 전기 공고(5~10월 월 250~350건 중 나라장터분)를 과거분 모드에서 대조용으로 계산해 내린다. 그 뒤로는 새로 들어오는 겹침만 계속 모니터링한다. 대조용 계산은 기초금액 API 호출이 공고당 1회 더 들어 과거분 예산에 포함한다(§6).

## 8. 화면

- **화면 노출은 §7 대조 합격 뒤에 켠다(사용자 결정 2026-10-23).** 그 전에는 수집·계산·대조만 돌고 화면은 지금과 같다. 켜고 끄는 스위치는 빌더가 정한다(코드 상수든 설정 행이든, 끄면 바로 원래 화면으로 돌아갈 것).
- **켜면 집계에도 포함한다(사용자 결정).** G2B 양식의 발주처별·연도별·전체 빈도와 강조 등급, 투찰 카드 1위 이력의 분위수에 자동 행이 함께 들어간다. 대신 집계가 보이는 곳마다 "자동 N건 포함"을 표기한다(N = 그 집계에 들어간 자동 행 수).
- **G2B 양식 탭**과 **투찰 카드의 발주처 1위 이력**만 새 테이블을 읽는다. 앱 로드 시 새 테이블을 한 번 받아(경기 전기만이라 수천 행 이하), 엑셀 행이 없는 공고에 한해 기존 행 목록에 합쳐 넘긴다.
- 예측 엔진에 들어가는 기존 `recs`(통계·추천 계산)는 손대지 않는다. 합친 목록은 위 두 화면 전용으로 따로 만든다.
- 자동 행 표시: 행에 '자동' 배지(작게, 툴팁 "나라장터 자동 수집 · 계산값 · 엑셀 대조 중"). 상세 모달에도 같은 표시. 배지 모양은 빌더 판단.
- 재료 부족으로 미완성인 행은 화면에 보이지 않는다(발주처사정율이 없는 행은 원래도 집계에서 빠진다).

## 9. 2단계 (이번 범위 아님, 방향만)

검증 합격 후 자동 행을 예측 엔진 입력에 넣는다. 그때 같은 공고 두 줄 문제(엑셀 `R…-000`과 API `R…`)를 함께 정리해야 한다. 지금도 10/9~20 엑셀 95건 중 41건이 API 행과 중복 존재. 삭제 금지라 플래그로 정리. 예측값이 바뀌므로 predict-architect → /evaluate → deploy-gate 전 과정을 거친다. 배지 제거도 이때 결정.

## 10. 하네스 분류 (예상)

- 1단계는 예측 코드·저장값을 바꾸지 않으므로 Neutral 예상. 다만 신규 기능이라 착수 전 predict-architect 검토를 받는다(CLAUDE.md 1단계).
- 서버 쪽(edge function·cron·테이블)은 git 밖이므로 마이그레이션 SQL과 함수 소스를 저장소(`supabase/migrations`, 함수 소스 사본)에 남긴다. 저장소에는 아직 `supabase/functions`가 없다. 기존 함수(`fn-collect-results`의 `_shared/g2b.ts`·`db.ts` 등) 소스는 배포본에서 받아 와서 재사용한다.
