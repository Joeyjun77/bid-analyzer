# 입찰 운영 깔때기 재설계 (데이터·업로드 제외 전면 재편)

날짜: 2026-10-22
상태: 초안 — 사용자 승인 대기 (승인 전 코드 변경 금지)
분류: 전달층(UI)·평가층(성적표) 재편. 예측 엔진(predict_v6, bid1st_v2, 안착안, pred_bias_map, 낙찰하한율 함수) **무변경**. 단, 공고 정렬·배지에 쓰는 "관내·소경쟁" 판정은 추천값에 영향이 없으므로 Evaluator로 분류한다. Generator 영역을 건드리는 순간 CLAUDE.md 1~4단계 하네스가 그대로 적용된다.

## 0. 왜 다시 설계하는가 (2026-10-22 점검 결과)

사용자 불편: "예측 메뉴에 숫자는 많은데 참고할 내용이 없다. 간단히 전달돼야 하는데 안 된다."

코드 점검:
- 상단 탭 12개, 예측 상세 모달 하위 탭 5개. "상세" 탭 하나에 숫자 30개 이상.
- 서로 다른 시기의 예측 엔진 4종(V6 opt_adj, v7/v7.2 3종 전략, 발주사 하한 V1, V2 안착/공략)이 폐기 없이 한 화면에 누적.
- 2026-05 `docs/v2/V2_UI_SPEC.md`가 이미 "추천값 하나, 3종 전략 폐기, 패널 하나"로 결정했으나, 숨은 "V2 미리보기" 탭의 목업(RecommendPanel·WhyPanel)에서 멈춤.

자사 성적표(`bid_details` 967건, 2025-11-03 ~ 2026-06-01, SUCVIEW "나의업체" 행):

| 항목 | 수치 |
|---|---|
| 하한 미달 실격 | 386건 / 967 (40%) |
| 참가자 수 중앙값 | 3,238개사. 3,000개 이상 공고가 596건(62%) |
| 1위 / 10위 이내 | 1건 / 12건. 10위 이내 전부 참가자 약 220개사 공고 |
| 참가자 3,000개 이상 공고에서 10위 이내 | 596건 중 1건 |
| 앱 추천값(±0.05%p) 대로 투찰 | 매칭 265건 중 25건(9%) |
| 고양 관내 142건 | 실격 74건(52%). 자사 가정 사정률 중앙값이 실제보다 약 0.4%p 낮음 |
| 고양 관내에서 자사 가정 − 실제 사정률 ∈ [0, +0.5%p] | 24건 중 10위 이내 7건. 그 밖 구간은 0건 |

태찬산업공사 과거 낙찰 14건(2012~2023): 11건이 고양시 관내 제한 공고(참가 150~250개사). 2024년 이후 0건. 같은 관내 공고는 연 240~250건 계속 발주 중.

결론: 낙찰 0건은 엔진 고장이 아니라 **포트폴리오(3,000개사 공고 62%) + 실격 40%**의 수학적 귀결이다. 사정률 예측 정밀도는 레버가 아니다. 레버는 ① 관내·소경쟁 공고를 빠짐없이 잡고 ② 하한 아래로 떨어지지 않으며 ③ 그 결과를 매달 수치로 보는 것이다.

### 6.2 오늘의 공고 (메인, 표 한 장)

행 = 공고 1건. 데이터원: `notices`(나라장터 자동 수집) + `bid_predictions`(예측 등록분) + 엑셀 업로드 예측분. 기존 공고 탭과 예측 리스트를 한 표로 합친다.

열(좌→우): 구분 배지 · 개찰일 · 발주처 · 공고명 · 기초금액 · 예상 참가자수 · 추천 사정률(100%) · 투찰금액 · 하한 통과 확률 · 상태

- **구분 배지**: `관내·소경쟁` / `일반` 2값. 판정 = 예상 참가자수 p50 < 300 **또는** 공고명·발주처에 자격 키워드 포함. 자격 키워드는 설정값(기본 `["고양"]` — "고양시"는 고양교육지원청을 놓치고 "관내"는 타 도시 제한 공고까지 잡으므로 제외. 로컬스토리지, 오늘의 공고 상단 톱니 아이콘에서 편집 — 권한 불필요. P1에서는 성과 탭에서 편집). 예상 참가자수는 기존 `participantCount.js`의 `resolvePcDist` 그대로 사용. 참가자 예측이 없으면 키워드만으로 판정.
  - [설계자 결정] 기존 코드와 같이 기관유형 평균(`AT_BA`) grain으로 잡힌 p50은 소경쟁 판정에서 제외한다(발주기관 기록 없음 = 모른다). 배지는 기관유형 무관하게 적용한다(배지는 참가자 수에 관한 것). 실측 1순위율(`pcWinRateOf`) 표시는 기존대로 지자체에만. 참가자 구간 상수(100/400)는 1순위율 밴드용으로 그대로 두고, 배지 경계 300은 별도 상수로 둔다(근거: §0 — 성적이 나온 공고는 전부 참가자 300 미만). 기존 "저경쟁(<100)" 필터는 "관내·소경쟁" 필터로 대체한다.
- **기본 정렬**: 관내·소경쟁 먼저 → 개찰일 오름차순. 필터 기본값 = "개찰 예정".
- **추천 사정률·투찰금액·하한 통과 확률**: `source='file_upload'`(입찰서류함 엑셀 업로드) 예측 행에만 채운다. 값은 현재 메인 추천(안착안, `bid1st_v2_*`/`b_pred_*` + `passProb.js`)과 동일 경로. 새 계산 없음.
  - [설계자 결정] 나라장터 자동 수집 공고(`g2b_auto`/`g2b_manual`)는 기초금액이 0이라 투찰금·통과확률을 낼 수 없고, 메인 추천 백필도 업로드 행에만 돈다(`App.jsx` recommendMain, getFinalRecommendation 격리 주석). 이 행들은 추천 3열을 "—"로 두고 상태를 `엑셀 업로드 필요`로 표시한다. 기존 공고 탭의 `pred_adj_rate + WIN_OPT_GAP` 표시는 제거한다(추천값이 두 종류가 되는 것을 막기 위해). 클라이언트에서 추천을 새로 계산하는 선택지는 Generator 변경이라 채택하지 않는다.
- **하한 통과 확률**: 90% 미만이면 행 전체를 경고색. 이것이 행에서 가장 눈에 띄는 숫자다.
- **상태**: 엑셀 업로드 필요 / 예측됨 / 개찰 완료(매칭) 3값. 개찰 완료 행은 기본 필터에서 숨김.
- **업로드 진입**: 표 상단에 "입찰서류함 엑셀 업로드" 버튼(기존 `loadPredFiles` 핸들러 그대로). 데이터 탭에도 같은 드롭존을 둔다.
- 기존 예측 리스트 기능 중 **유지**: 엑셀 내보내기, 예측 삭제, 유찰·수의 숨김 토글, 개찰 완료 행의 예측–실제 비교(행 펼침). **제거**: 주력 발주사 필터(관내·소경쟁 배지가 대체), 등급(S/A/B) 필터.
- 행 클릭 → 투찰 카드. 표에서 바로 나라장터로 옮겨 적을 수 있어야 하므로 사정률·투찰금은 복사 가능한 모노스페이스 텍스트.
- 한 행에 숫자 6개(기초금액·참가자수·사정률·투찰금·통과확률·개찰일). 더 넣지 않는다.

### 6.3 투찰 카드 (공고 클릭 시, 모달 또는 우측 패널 — 빌더 선택)

3블록 고정. 기존 "상세" 탭의 30개 숫자는 아래에 없으면 삭제.

**블록 1 — 추천 (RecommendPanel 재사용)**
- 추천 사정률(100% 기준, `fmtAdj` 듀얼 표기 보존), 투찰금액, 하한 통과 확률(막대), 모드 배지(안착/공략), 모드 안내문 1줄.
- 관내·소경쟁 공고에 한해 보조 1줄: "이 발주처 실제 사정률 분포 P25~P75 = a~b, 추천은 그 안/밖". 데이터원 = 기존 `buildAdjHistory`. 표시 전용.
- 접기(▸ 근거): 매칭 단위(발주사×금액대 / 발주사 / 유형), 표본 n, 신뢰도, 2순위 안(사정률·투찰금), 자사 유효 하한율 듀얼 표기. WhyPanel 재사용.

**블록 2 — 경쟁 구도**
- 예상 참가자수(p50, p25~p75, 근거 grain)와 그 구간의 실측 1순위율(`pcWinRateOf`).
- "참여사 분포 보기" 버튼 → 기존 `ParticipantMatrixModal`(점분포) 그대로 호출. 경쟁사 검색 기능 포함.

**블록 3 — 1위 사정률 이력**
- 이 발주처의 최근 N건(기본 20) 1위 사정률(`br1`)과 발주처 사정률(`ar1`) 목록 + P25/P50/P75 요약. 기존 "발주사 이력 분석 패널" 로직 재사용.
- "G2B 양식에서 전체 보기" 링크 → G2B 양식 탭으로 해당 발주처 선택 상태로 이동.

카드 어디에도 "낙찰 확률" 문구는 Mode B에서 나오지 않는다(기존 게이트 유지).

### 6.4 성과 (자사 성적표)

데이터원: `bid_details`(SUCVIEW 업로드로 생성, `my_rank`·`my_bid_rate`·`my_adj_rate`·`adj_rate`·`floor_rate`·`participant_count`) + 관내 공고 모수는 `bid_records`에서 자격 키워드·참가자수로 필터. 전부 클라이언트 집계(행 수 수천 이하). 사정률 컬럼은 전부 0 기준(`adj_rate`·`my_adj_rate`·`win_adj_rate` 모두 "-1.14" 형식, 2026-10-22 DB 확인).

집계 정의(§0 수치 재현 기준):
- 투찰 수 = `bid_details` 행 수(SUCVIEW는 자사가 참여한 건만 내보내므로 행 = 자사 투찰 1건).
- 통과 = `my_rank >= 1`. 실격 = 그 외(null 또는 0). §0의 386은 "`my_bid_rate < floor_rate`"로 센 하한 미달 건수이고 `my_rank` null 415건 중 386건이 이에 해당한다. 성과 화면은 "통과율"을 1차로 쓰고, 하한 미달 건수는 보조 열로 따로 센다.
- 관내 = 발주처명(`ag`) 또는 공고명(`pn`)에 자격 키워드 포함(§6.2와 같은 키워드). §0의 142는 `ag LIKE '%고양%'`만 센 값이고, 공고명까지 보면 146건(통과 아님 74건)이다. **P1 재현 기준 = 전체 967 · 하한 미달 387 · 키워드 일치 146(통과 아님 74)** (2026-10-22 DB 확인. 967건 중 pn_no 중복 0, 음수 순위 0, 0순위 2, `|my−win| > 5` 이상치 2).
- 소경쟁 = 개찰 후 **실측** 참가자수(`participant_count`) < 300. 오늘의 공고 배지는 사전 예측값(p50)을 쓰고 성과 화면은 실측을 쓴다. 둘의 차이는 커버리지 해석 시 각주로 표시한다.
- 관내·소경쟁 행 그룹: **투찰(분자)** = 관내 또는 소경쟁(§6.2 배지 정의와 동일). **공고 모수(분모)와 커버리지 분자** = 키워드 일치만. 전국의 참가자 300 미만 공고는 자사 자격 밖이라 분모에 넣으면 커버리지가 2%대로 왜곡된다(2026-10-22 브라우저 실측 후 정정). 일반 그룹의 커버리지는 정의상 무의미하므로 표시하지 않는다.

월별 표, 행 = 월, 열 그룹 2개(관내·소경쟁 / 일반):

| 열 | 정의 |
|---|---|
| 공고 수 | 해당 월 개찰된 관내·소경쟁 공고 수(`bid_records`) |
| 투찰 수 | `bid_details` 자사 행 수 |
| 커버리지 | 투찰 수 / 공고 수 |
| 통과율 | `my_rank is not null` 비율 |
| 1위 근접 | 통과 건 중 `my_bid_rate − win_bid_rate ≤ 0.5` 건수 (bid_rate 공간). §0의 "가정 − 실제 사정률 ∈ [0, 0.5]"은 진단용 분석이며 KPI로 쓰지 않는다(adj_rate 공간 WIN-zone KPI 신규 추가 금지, predict-architect 2026-10-22 지적) |
| 10위 이내 / 1위 | `my_rank ≤ 10` / `= 1` |
| 간격 중앙값 | 통과 건의 `my_bid_rate − win_bid_rate` 중앙값. 입력 오류 방어로 절대값 5 초과는 제외 |

상단 요약 카드 3개: 최근 3개월(업로드 있는 달) 관내·소경쟁 커버리지, 통과율, 1위 근접률. 각 카드에 표본 n 병기(월 20건 안팎이라 비율만 보면 오독). 숫자 외 해설 1줄씩(예: "통과율 90% 미만이면 가정 사정률을 올려야 합니다").

데이터 취급 규칙(predict-architect 지적 반영):
- `bidDetails`·`recs`는 App.jsx가 이미 로드한 state를 prop으로 받는다. 새 REST 호출 없음.
- 두 배열은 예측 엔진(`predictV5`) 입력과 공유되므로 **제자리 정렬·변형 금지**(`[...arr].sort`만 허용).
- 두 배열 모두 `pn_no` 기준 중복 제거 후 집계(페이징 동률·legacy 중복 방어).
- `recs` 모수에서 `is_excluded` 행과 낙찰자(`co`) 없는 유찰 행 제외.
- 커버리지는 분자(실측 참가자수)·분모(`pc`) 분류 기준이 달라 100%를 넘을 수 있음을 각주로 표시.

데이터가 없는 달은 "업로드 없음"으로 표시해 업로드 공백을 드러낸다(현재 2026-06 이후 공백).

### 6.6 데이터·DB

- 신규 테이블·컬럼 없음.
- 자격 키워드는 로컬스토리지(기존 own_score와 같은 방식). DB 저장은 하지 않는다.
- 성적표 집계는 클라이언트. `bid_details`는 App.jsx가 시작 시 로드하는 `bidDetails` state를 그대로 쓴다(새 REST 호출 없음).
- predict-architect 분류(2026-10-22): P1 = Evaluator, 회귀 위험 低, `/evaluate` 면제. 조건 = Generator 함수 diff 0줄 + 위 bid_rate 공간 정의.

## 8. 열린 질문 (사용자 답 필요)

1. 2026-01-15 일산동구 보안등 공고: 자사가 1순위 금액(89.7661%)이었으나 낙찰자는 이룸일렉트릭. 동일 금액 추첨 패배인지, 적격심사 서류 탈락인지. 후자라면 성과 화면에 "1위 후 탈락" 열과 투찰 카드에 적격 체크리스트가 필요하다.
2. 일상 투찰 흐름: 공고마다 입찰서류함 엑셀을 올려 예측을 만드는지(file_upload), 아니면 나라장터 자동 수집 공고의 "예측 등록" 버튼을 주로 쓰는지. 후자가 주력이면 §6.2의 "자동 수집 행은 추천 빈칸" 결정이 업무를 막으므로 다시 정해야 한다.
